# 要件（Requirements）

もとにした文書: 意図の整理 `intent-statement.md`、範囲 `scope-document.md`、既存サイトの読み解き `business-overview.md`・`architecture.md`・`code-structure.md`（と `code-quality-assessment.md`）、作業の決まりごと `team-practices.md`、依頼文 `aidlc-prompt.md`。回答は requirements-analysis-questions.md の Q 番号で示します。

## 1. 何を達成したいか（Intent analysis）

- 珍しい熱帯魚1種類ごとに、世界中の記録を日本語で出典つきの1ページにまとめ、少しずつ積み上げる（intent-statement.md）。
- 今回の作業のゴールは、その積み上げを毎回同じ品質で回すための土台を作ること。具体的には、種ページの型・確認の仕組み・手順書・次の候補（scope-document.md の S-1〜S-9）。
- 2種類目以降の執筆と本公開は、今回の範囲の外（scope-document.md）。

## 2. 機能の要件（Functional requirements）

### FR1 種ページの型（テンプレート）

| ID | 要件 | 合否の判定 | 出どころ |
|---|---|---|---|
| FR1.1 | 種ページには必ず次の章がこの名前の範囲で入る: 要点の表、生息地の環境、繁殖記録の比較、飼い方・殖やし方、まだ分かっていないこと、参考文献。並び順は型で決め、全種で同じにする | 書き出した種ページすべてで、6つの章の見出しが型の順に並んでいる | Q1、scope S-1 |
| FR1.2 | 要点の表の項目と順番は型の側で1か所に決め、全種で同じにする。原稿に値がない項目は消さずに「記録なし」または「未確認」と表示する | 種ページすべての要点の表で、項目名と順番が同じ。値のない項目は空欄ではなく「記録なし」か「未確認」 | Q7、code-quality-assessment F7 |
| FR1.3 | 繁殖記録の比較は表にし、列は「誰が・いつ・どんな水で・きっかけ・卵の数・孵化までの日数・稚魚の育て方・失敗例」とする。分からない欄は「記録なし」と書く | 比較表の列見出しがこの8項目（と出典）になっている | Q1、aidlc-prompt.md |
| FR1.4 | 本文の出典番号［n］は、同じページの参考文献 n 番へのリンクになる | ［n］を押すと参考文献の n 番の位置へ移る。リンク先の番号がない［n］は確認で失敗になる（FR9.4） | Q7、code-quality-assessment F3 |
| FR1.5 | 種ページには公開日と更新日を表示する | 書き出したページに公開日と更新日が `YYYY-MM-DD` で出る | scope S-1、既存の single.html |
| FR1.6 | 学名は属名と種小名だけを斜体にし、「sp.」「（旧 …）」などは斜体にしない | CW111 のページで「Hoplisoma」は斜体、「sp. (CW111)」「（旧 Corydoras）」は斜体でない | Q7、code-quality-assessment F6 |
| FR1.7 | 情報の確かさは、今の書き方（本文に「要確認」「未確認」「近縁種のデータ」「（推論）」）で示す。参考文献ごとの段階は付けない | 型に参考文献ごとの段階の欄がない。4つの表示は原稿で使える | Q2 |
| FR1.8 | 深く調べる版と浅く調べる版は、同じ章をすべてそろえる（浅い版は中身が少なくてよい） | 浅い版の原稿でも FR1.1 の6章がそろう | Q4 |
| FR1.9 | 型には有料ガイドへの誘導枠を置かない | 書き出したページに有料ガイドの案内枠がない | scope-document.md（範囲外: 有料販売） |

### FR6 調査と執筆の手順書

| ID | 要件 | 合否の判定 | 出どころ |
|---|---|---|---|
| FR6.1 | 1種類を「調べる → 突き合わせる → 書く → 確かめる → 公開する」の順で回す手順を書く | 手順書に5つの段階があり、それぞれにやることと終わりの目安がある | scope S-3、aidlc-prompt.md |
| FR6.2 | 深く調べる版と浅く調べる版の2つの進め方を書き、どちらを使うかの決め方も書く | 手順書に2つの版と、選び方が書かれている | approval-handoff Q1 |
| FR6.3 | 深い版の公開の線: 一次記録（論文、または本人による繁殖・飼育の記録）が1件以上あり、要点の表の数字すべてに出典があり、海外と国内の両方の記録がある | 手順書の確認項目にこの3つがある | Q3 |
| FR6.4 | 浅い版の公開の線: 深い版と同じ6章をすべてそろえる | 手順書の確認項目にある | Q4 |
| FR6.5 | AI がまとめた文と、AI が出した引用・数字を原文と並べて確かめる手順を書く。引用は短い一文までにし、「」で囲んで出典を付ける | 手順書の「確かめる」段階にこの手順がある | team-practices、project.md の Mandated |
| FR6.6 | 1種類にかかった時間を段階ごとに記録する欄を用意する | 手順書に記録の欄がある | feasibility（R-1 の対策）、approval-handoff Q1 |
| FR6.7 | 使う道具（ブラウザ、yt-dlp による字幕取得、検索、AI）と、それぞれの注意点を書く | 手順書に道具と注意点の一覧がある | aidlc-prompt.md |
| FR6.8 | 手順書は git に入れず、手元のフォルダ（例: `notes/`）にだけ置く。そのフォルダを `.gitignore` に入れる | `.gitignore` にそのフォルダがあり、`git status` に出ない | Q6、Q9 |

### FR9 確認の仕組み

| ID | 要件 | 合否の判定 | 出どころ |
|---|---|---|---|
| FR9.1 | `hugo` で書き出したとき、エラーも警告も0件であることを確かめる | 確認を実行すると、エラー・警告があれば失敗する | team-practices（Testing Posture） |
| FR9.2 | 書き出したページを調べるプログラムを作る。少なくとも FR3.1〜FR3.6 の不具合の再発と、全ページの noindex を確かめる | 不具合を戻すと確認が失敗し、直すと通る | team-practices、D1〜D5 |
| FR9.3 | サイト内のリンク切れを確かめる | 存在しないページへのリンクを入れると確認が失敗する | team-practices |
| FR9.4 | 文章のルールを確かめる: 本文の［n］がすべて参考文献にある、要点の表の数字に出典がある | 参考文献にない［n］を入れると確認が失敗する | team-practices、project.md の Mandated |
| FR9.5 | 確認は自分のパソコンで1つのコマンドで実行でき、GitHub Actions でも push のたびに自動で動く | 手元で1コマンドで全部動く。GitHub の push で同じ確認が走る | team-practices（確認を動かす場所） |

## 4. 制約（Constraints）

- 公開先は GitHub Pages（main の /docs）、作り方は Hugo のまま（build-vs-buy.md、constraint-register.md C-01）。
- 作るのも決めるのも本人1人。AI は一時ブランチで作業し、push は本人がする（team-practices）。
- 文章の決まり（出典、要確認・未確認、合法性を断定しない、販売店をおすすめしない、許可なく転載しない、など）は project.md の Mandated・Forbidden に従う。
- 期限はない（scope-document.md）。

## 5. 前提（Assumptions）

- 要点の表の項目は、依頼文の「流通名・分類・産地・大きさ・水温・繁殖・相場」と今の CW111 の項目をもとに、テンプレートの設計で確定する（aidlc-prompt.md、既存の原稿）。
- 比較ページで種をまたいで比べる仕組みは、原稿のフロントマターに繁殖記録をデータとして持たせる形が向いている（推論）。形はテンプレートの設計で決める。
- GitHub Actions は公開リポジトリなら無料の範囲で使える（team-practices）。

## 6. 範囲の外（Out of scope）

- 有料販売、広告・アフィリエイト、「水面」との連携（intent-statement.md）。
- 2種類目以降の調査と執筆、本公開（scope-document.md）。
- 参考文献ごとの確かさの段階表示（Q2 で付けないと決めた）。
- note・Instagram への投稿そのもの。

## 7. まだ決まっていないこと（Open questions）

- 深い版・浅い版のどちらで書いたかを、ページ上で読者に見せるかどうか（テンプレートの設計で決める）。
- 月1回の更新のまとめをどこに載せるか（意図の整理から持ち越し）。更新履歴ページは自動の一覧だけと決めた（Q8）。
- masukoap とレプスキの URL（市場調査から持ち越し）。
- 次の10種類の候補を選ぶ基準から「日本で売られている」「検索する人がいる」を外した（Q5）。読者の規模の見積もり方は未定のまま（市場調査）。
